# Reusable analysis and scenario toolkit

Use these helpers for repeated processing. Ordinary reading, editing, searching, and diagnosis still use Codex directly. The documentation MCP remains the authority for MQL5 facts. The helpers are shell commands, not new MCP tools. No new Python environment or dependency is needed; use the shared environment described in SKILL.md. All Python modules use the standard library and Python 3.12 or newer.

## Commands and evidence

Invoke `scripts/mql5_toolkit.py` with the shared Python launcher. The six operations are:

```
report read --input <absolute-report.htm> [--tester-result <absolute-smoke-result.json>] --output <new-absolute-directory>
report compare --baseline <absolute-report.htm> --candidate <absolute-report.htm> [--baseline-result <absolute-json>] [--candidate-result <absolute-json>] [--expectations <absolute-json>] --output <new-absolute-directory>
includes inventory (--project-profile <absolute-profile.json> | --root <absolute-project-directory>) [--entrypoint <absolute-mq5>] [--include-root <absolute-standard-include-directory>] [--powershell <absolute-host.exe>] --output <new-absolute-directory>
includes compare --baseline <absolute-snapshot-result.json> --candidate <absolute-snapshot-result.json> --output <new-absolute-directory>
profile read --input <absolute-native.csv> [--conditions <absolute-json>] --output <new-absolute-directory>
profile compare --baseline <absolute-native.csv> --candidate <absolute-native.csv> [--baseline-conditions <absolute-json>] [--candidate-conditions <absolute-json>] [--expectations <absolute-json>] --output <new-absolute-directory>
```

Repeat `--entrypoint` and `--include-root` only in explicit inventory mode. Profile mode reuses the existing PowerShell profile validator and saved selections. Without explicit entrypoints, inventory discovers known `.mq5` files under the selected root. Multiple standard roots are an inventory convenience: multiple matching files are ambiguous, not a compiler search-order claim.

The saved profile's `include_path` names the compiler's MQL5 root. Profile inventory searches its `Include` child for angle-bracket headers, matching compilation; explicit `--include-root` names the directory containing those headers directly. Files in the MQL5 root cannot substitute for standard headers. A missing `Include` child leaves angle includes unresolved while retaining known local sources; a linked child is disclosed as uncertainty without traversing its target. An omitted profile include path supplies no inferred standard roots.

Every operation reserves a new output directory, whose parent must exist, and writes `result.json` and `summary.txt`. It leaves evidence inputs unchanged. CLI paths must be absolute. Paths inside manifests resolve relative to the manifest. Scripts find sibling resources from their own installation directory. Output schema 1 includes the operation and detailed statuses. Finite decimal values are strings; `missing`, `undefined`, `special`, and `unparseable` remain distinct. Calculations use decimal arithmetic with 50 significant digits.

A percentage suffix cannot replace an explicitly required currency, ratio, count, sample, or millisecond unit. Such a report measurement is `unparseable`, retaining its raw text, expected `unit`, `reported_unit`, and reason; expectations using it are `not_evaluable`. A percentage in recorded deposit or elapsed-duration settings is invalid input. Native percentage fields retain their percent values.

Tester-result, profiler-conditions, comparison-expectation, and include-snapshot JSON fingerprints use the exact byte buffers consumed by their readers. If another process changes a file after it is read, the fingerprint continues to describe the analyzed snapshot rather than the later file contents. Separate inputs are not read as one atomic transaction.

JSON decimal numbers retain their numeric type and exact value during validation and comparison; they cannot satisfy fields that require strings. Results serialize finite decimals as strings. Comparison differences include `type_differences` paths when JSON types differ, so numeric values remain distinguishable from strings in the published evidence.

JSON keys and string values must decode to valid Unicode text. Escaped unpaired surrogates are invalid input and produce exit code 2 with complete failure JSON and a summary. Valid literal Unicode and escaped surrogate pairs retain their text; evidence input bytes remain unchanged. Saved project profiles use the same Unicode requirement: their shared validator rejects invalid escapes before converting JSON or selecting compilation/tester inputs. Profile validation uses the existing exit-code-2 diagnostic contract rather than analysis result artifacts.

Exit codes: `0` processing completed, `1` explicit expectations failed, `2` invalid input/tooling, `3` incompatible comparison, `4` insufficient evidence or unevaluable expectations. Comparison compatibility takes precedence over expectations. Read success describes processing, including disclosed linkage issues; inspect `evidence_linkage` before using recorded run settings. Console summaries are bounded; inspect the JSON for complete measurements, provenance, and issues.

An I/O failure while saving analysis, journal, or batch outputs returns `2` with a bounded error message. This includes the batch progress checkpoint and combined results table. Retained files may be partial, including a complete processing result followed by a failed summary write. Check the process exit code before treating the operation as complete; retained parsing or comparison statuses do not establish successful evidence publication. A failed final checkpoint preserves earlier progress and records `output_publication_failed` in the final result when that result can still be saved. Input evidence remains unchanged.

The Python CLI writes UTF-8 to stdout and stderr, including redirected pipes. Unicode evidence paths remain readable without changing the operation's exit status because of a legacy console encoding.

The PowerShell journal and scenario helpers reuse the tester's native exclusive directory creation. A folder created by another writer after the initial path check is refused before claiming it or writing artifacts, preserving that writer's evidence.

## Reports and comparisons

Supported input is the English native MT5 HTML Settings/Results table layout covered by repository trading and no-trade fixtures, encoded as UTF-16LE with BOM or UTF-8. Nested/malformed tables, ambiguous duplicate statistics, and other layouts/languages are rejected. Table, row, and cell elements must close in their nesting order; unmatched or mismatched closures are invalid input. Individual absent fields remain missing. Do not use a no-trade fixture alone to validate trading statistics. Source hashes identify exact analyzed bytes, including encoding.

Native labels, values, units, table/row/cell locations, input rows, reported dates, and available terminal-build headers remain in the JSON. Balance and equity drawdowns, amounts and percentages, trades and deals are separate. Native statistics are extracted rather than recalculated; for example a profitable-only native report can record profit factor `0.00`. This value is preserved.

EA input text preserves decoded spaces, tabs, and line breaks, including the first `Inputs` value and continuation rows. A native value contained in one bold span retains its internal whitespace while layout padding outside that span is ignored. Unwrapped or partially bold values retain the complete decoded cell text. Different input text makes the comparison `incompatible` and expectations `not_evaluable`; numeric statistic normalization remains separate from input text.

Count measurements (trades, deals, bars, ticks, symbols, and the trade-count parts of percentage pairs) require nonnegative integer values. Negative or fractional counts retain their raw text, unit, and source cell as `unparseable` with reason `invalid_count`; differences and expectations using them cannot be evaluated. Valid zero counts and whole-valued decimal/scientific representations remain available. Missing, undefined, and special values retain their separate states. Monetary, ratio, and percentage measurements keep their existing semantics. The integer trade/deal definitions were verified in Testing Statistics, `mql5:5d601e80c813390731537704:s000`, under index `ec0dbca96e12f4d877dd33b7593158c61156cb7b490b42bf559bf97445f83339`.

Terminal build metadata comes from single-cell report headers before `Settings`. EA names and input text such as `(Build 9001)` retain their role as configuration values. Missing build headers remain missing evidence; multiple build headers in the report preamble are ambiguous and invalid input.

An optional existing tester result uses schema 2. Its recorded report hash and length must match before settings or artifact hashes are associated. A copied report may have a different path; bytes establish linkage. Root source, EX5, and preset hashes are recorded identities, not proof that their files still exist. Parsing, recorded tester status, linkage, comparability, and expectations are separate. Report existence never proves tester completion. Requested dates remain separate from reported coverage.

Malformed nested records, invalid hash strings, and nonfinite recorded deposits are invalid input. Missing optional records remain evidence gaps. SHA-256 hex case is normalized for matching while the recorded report evidence is preserved.

Recorded `execution_mode` accepts integer `-1`, matching the existing tester and project-profile interfaces. Its signed value remains distinct from `0` and positive fixed delays during comparisons. Values below `-1` and non-integer values are invalid. The random-delay meaning was `Not verified in the installed MQL5 CHM`; it was verified in MetaQuotes' [How to Start the Trading Platform](https://www.metatrader5.com/en/terminal/help/start_advanced/start), under the tester configuration settings. Importing this setting does not verify execution or make differing delay settings comparable.

Required comparison conditions are symbol, period, reported dates, model, deposit, currency, leverage, execution mode, and effective input rows. A known difference is `incompatible`; missing conditions are `insufficient_evidence`; matching conditions are `comparable`. Report/run conflicts are gaps. Artifact identity changes do not make code-revision comparisons incompatible. Terminal and data-quality information is retained separately and can be explicitly required.

Deposit conditions use an exact decimal identity: trailing fractional zeros and equivalent zero signs are removed without rounding input digits. Distinct accepted finite amounts cannot become equal through the arithmetic context. The original deposit text remains in the configuration evidence.

Copy [the expectation template](../assets/comparison-expectations.template.json) into the project and replace its example bounds with independently specified requirements. Schema 1 has a nonempty `metrics` array. Each item has `metric`, `target` (`candidate`, `difference`, or `percentage_difference`), and one or both decimal-string `minimum`/`maximum`. Unknown fields, nonfinite bounds, and duplicate JSON keys are invalid. Percent difference is `(candidate-baseline)/abs(baseline)*100`; zero baseline makes it undefined while signed/absolute differences remain available. Missing metrics produce `not_evaluable`. Results are `pass`, `fail`, `not_evaluable`, or `not_requested`; lower profit alone is only an observed difference.

Optional `required_conditions` can add `terminal_image_sha256`, `terminal_build`, `history_quality`, `bars`, `ticks`, or `symbols`. `required_evidence` accepts `linked_run`, `source_hash`, `expert_hash`, `preset_hash`; `require_successful_runs` requires linked recorded successful smoke statuses, without turning them into independent execution verification.

Required numeric data-quality conditions compare their exact values, so equivalent formatting such as `99%` and `99.00%` does not create an incompatibility. Original statistics and labels remain in the report evidence.

## Include inventory

Literal `"file"` includes use the directory of the file containing the directive, as described in AlgoBook 2.9.1 Including source files (#include), `mql5book:aef4e438f31b5d6ac50e4100:s000`, and observed in the native build 6235 nested-header fixture. The Reference topic Including Files (#include), `mql5:3d2e853ca7e9b5fc6c2d1c7e`, uses main-source wording. The inventory conservatively retains a different existing main-source candidate as uncertainty, scanning both possible consumers rather than claiming compiler selection. Both passages were verified under index `ec0dbca96e12f4d877dd33b7593158c61156cb7b490b42bf559bf97445f83339`. Literal `<file>` includes use explicitly selected standard Include roots. Comments and ordinary strings cannot declare include edges.

The snapshot records project source hashes, reachable external sources, declared edges, conditional context, possible consumers, cycles, unresolved or unsupported forms, and unselected entrypoints. Conditional branches remain possible; macros are not expanded. Explicitly selected directories are canonicalized. Linked entrypoint files retain their alias, and links encountered during discovery or include resolution are disclosed without reading their targets. Linked include candidates retain their alias and linked component as uncertainty. Bounds are 50,000 project files, 10,000 source files, 8 MiB per source, and 128 include levels. Unknown coverage requires further review. Cycles alone are not compilation errors.

Ordinary selected entrypoints use the filesystem's path spelling. Windows filename-case aliases share one recorded source identity with discovery, preventing duplicate source slots, false unselected entrypoints, and spurious snapshot changes. Linked paths retain their aliases for uncertainty checks.

Angle-bracket header names retain filename characters until `>` or the line end. An apostrophe in a name such as `<Owner's.mqh>` cannot start a character literal and hide following includes or conditional directives. MetaEditor build 6235 compiled this spelling and the following shared include in the nontrading `tests/fixtures/angle-include-filename` fixture, whose source hashes and sanitized compiler log are retained with provenance. Incomplete names remain unsupported dependencies; later directives remain visible.

LF, CRLF, and CR physical line endings are normalized only in the decoded scanner buffer. A line comment ends at each physical newline, subsequent includes and conditional directives remain visible, and source hashes still describe the original bytes. MetaEditor build 6235 compiled the nontrading UTF-8 and UTF-16LE BOM CR-only sources in `tests/fixtures/carriage-return-includes`, including the header following a line comment. The fixture retains source hashes and sanitized compiler logs with provenance. The Comments passage, `mql5:9657d25f31e210971393f5ef`, verified under the index above, specifies newline termination without enumerating byte encodings; the native builds establish the recorded CR support. Comparisons retain possible consumers of changed or deleted headers and continue to disclose unresolved dependencies.

Unicode NEL (`U+0085`), line separator (`U+2028`), and paragraph separator (`U+2029`) characters inside string text or literal header names remain part of their source line. They cannot split a header declaration or shift later include locations. The scanner splits only normalized physical LF, CRLF, or CR endings. MetaEditor build 6235 compiled the unchanged nontrading UTF-8 BOM and UTF-16LE BOM sources in `tests/fixtures/unicode-include-separators`; provenance retains their source hashes and sanitized logs. The String Type passage, `mql5:4195758c7d7a42d3a84b78cc`, and Including Files passage, `mql5:3d2e853ca7e9b5fc6c2d1c7e`, were read under the index above. Native compilation establishes these specific recorded characters and filenames; the inventory continues to report possible dependencies rather than exact compiler consumption.

Profile mode fingerprints the selected profile before calling the existing validator and checks it after validation and inventory. A changed profile stops the operation as invalid input. These boundary checks do not prove an atomic snapshot across concurrent changes.

When a shared source is read for multiple entrypoints, its consumed hash must remain the same. A changed hash stops inventory as invalid input, preventing declarations from different source versions from sharing one recorded fingerprint. Retry after source edits finish. This check does not establish an atomic snapshot of the whole project.

Directory enumeration failures retain their path and operating-system error number as `directory_scan_failed` issues. Scanned files remain available, but coverage is `uncertain`; include comparisons preserve unknown consumer coverage when either inventory encountered a scan failure.

All ambiguous literal candidates are inventoried, including candidates in multiple standard roots and their transitive includes. They retain uncertain resolution and possible consumers. Comparisons reject malformed file identities, consumer arrays, and missing coverage rather than inventing affected entrypoints.

Comparison uses exact absolute file identities and both snapshots' consumers, including deleted headers. Moved roots are disclosed and appear as removed/added files. An orphan source change has unknown consumer coverage. A snapshot is not proof of compiler consumption, runtime dependencies, or compilation success. Use affected entrypoints to select the existing compiler workflow.

## Journals

Run `Read-Mql5Journal.ps1 -TesterResultPath <absolute-smoke-result.json> -OutputDirectory <new-absolute-directory>`. Optional `-LiteralMessage` strings select literal, case-sensitive message substrings; filters are fingerprinted rather than printed. `-MaxBytes`, `-MaxLines`, and `-MaxGroups` bound processing. The helper reads only recorded UTF-16LE segments, verifies byte ranges and SHA-256, reuses the existing redactor, and masks application-marker plaintext.

Groups retain redacted message/component, inspected count, first/last recorded timestamp, and up to three evidence locations. Counts cover only inspected lines. Complete segments, partial verified segments, bounded excerpts, unavailable evidence, and truncation are separate; incomplete analysis returns `4`. Overlapping segments are not counted twice; ranges starting or ending inside a journal record disclose truncation even when their hashes match. Excerpts are fallback observations, not hash-verified full journals. Patterns do not prove root causes. Verify runtime error or trade-return interpretations through the MCP.

Overlap detection applies across both journal kinds and uses physical file identity from the opened handle, so hard-link aliases cannot count the same byte range twice. Segment results retain the observed `file_identity` alongside the original path when available; this identity is not a digest or proof of run association. Independent file copies and disjoint ranges remain separate evidence. Known overlaps are skipped before reserving buffer bytes, so duplicate segments alone do not exhaust the byte budget or imply truncation.

If a journal has no usable segments and a known overlap, its fallback excerpts are left uncounted because their independence from previously inspected bytes cannot be established. Offered excerpts then produce `overlap_excerpt_fallback_skipped`; fallback processing remains available for unavailable segments without a known overlap. The byte budget includes accepted fallback excerpts measured as UTF-16LE bytes; an excerpt that cannot fit is skipped and truncation is reported.

Group identities use ordinal comparison of the redacted journal kind, component, and message. Differences in case remain distinct. The tester-result source hash and length describe the exact captured JSON buffer passed through the existing metadata validator. The journal's `budgeted_bytes` counts attempted segment buffers and accepted fallback excerpts; a failed hash check, read, or decode does not release its reserved byte budget for later evidence.

Empty message or component fields are retained without stopping later observations. Application markers are masked in both fields before generic redaction can rewrite their nonces. Segment `hash_verified` records byte integrity separately from processing status: an observation-processing failure has status `processing_failed` and makes the evidence incomplete even when its bytes match the recorded hash.

## Scenario batches

Copy [the manifest template](../assets/scenarios.template.json). Schema 1 contains 1–100 scenarios, each with a unique filename-safe `id` and an existing project `profile` path. Optional paths: `expected_marker_file`, `baseline_report`, `baseline_result`, `expectations`. A baseline result requires its report; expectations require a baseline. No inline strategy overrides or second tester-settings schema are accepted. The complete manifest, profiles, markers, baselines, and expectations are validated before execution.

Scenario IDs contain 1–64 ASCII letters, digits, underscores, or hyphens, starting with a letter or digit. Windows device names and case-insensitive duplicates are rejected. The complete ID must match: a trailing newline or other control character fails validation for the entire manifest before any scenario compiles or starts testing. Valid IDs retain their exact spelling.

Batch marker files use the tester's shared strict UTF-8 reader (optional UTF-8 BOM), literal pass-protocol validator, and collection limits. Labels contain 1–64 ASCII letters, digits, underscores, dots, or hyphens. Files cannot exceed 65,536 bytes; select at most 64 markers totaling at most 8,192 characters. Blank lines are ignored; batches reject duplicate markers. UTF-16 files, unsupported labels, and exceeded limits fail the entire manifest before any scenario compiles or starts testing, including when the invalid selection appears after otherwise valid scenarios.

`Invoke-Mql5ScenarioBatch.ps1 -ManifestPath <absolute-json> -OutputDirectory <new-absolute-directory>` defaults to `-Action Validate`, without compiling or launching MT5. `-Action Execute` compiles the selected tester entrypoint immediately before each sequential run and passes its freshly emitted receipt to the existing tester. Optional `-PythonPath` selects an already existing interpreter; otherwise the shared environment is required. Execution carries the existing tester's artifact, configuration, and process requirements, without another permission prompt.

The result fingerprints the manifest before validation, each profile before reading it, and optional evidence before processing it. It rechecks those selections after validation and at compiler, tester, and analysis stage boundaries once owned-process cleanup is verified. A changed or unavailable selection stops subsequent execution and skips remaining scenarios. Checks at these boundaries do not establish an atomic snapshot across concurrent file changes. Unicode receipt paths are preserved across the supported PowerShell process boundaries.

Cleanup uncertainty stops subsequent compiler, tester, and analysis processes immediately. Retained report paths and an explicit analysis-skipped reason remain available for later inspection when this mandatory abort prevents report analysis.

Runner failure remains a failure even if a child records a zero exit code. Each analysis records processing status and a validated result path separately from the original process status/exit code. Missing or inconsistent analysis JSON fails analysis, and the combined table preserves compiler/tester exit codes and recorded tester status. A completed tester with no retained report fails analysis. Report/run hash or length mismatches also fail batch analysis while preserving the reader's original processing status and the tester's recorded completion.

Each scenario has separate outputs, original compiler/tester statuses and exit codes, and `completed`, `failed`, `timed_out`, `blocked`, or `skipped` status. Report analysis is retained separately: a completed tester can have failed analysis. Every retained HTML report is analyzed. Failure may continue only after owned-process cleanup is verified; uncertainty aborts remaining scenarios. `progress.json` records in-progress evidence separately from the final result. Optional absolute `-CancellationFile` causes remaining scenarios to be skipped when the file exists; current owned work finishes cleanup first. Hard host termination can leave only progress evidence and must not be called batch completion. Batch exit `0` means validation/completed results with successful analysis, `1` retained scenario/analysis failure, `2` configuration/tooling failure or aborted execution. Batch duration is orchestration evidence, not EA execution cost.

## Profiling

Supported input is native MetaEditor function-view CSV captured from build 6235: UTF-16LE BOM, semicolon delimiter, no header, six cells: function name (including recorded indentation), reported source line, Total CPU samples, Total CPU percent, Self CPU samples, Self CPU percent. Indented occurrences can repeat a function at a different reported line; they remain duplicate/uncertain mappings, not additional calls or a separately summable CPU total. Unsupported views/formats/encodings fail clearly. Sampling counts are neither function calls nor elapsed milliseconds. Hotspots rank by native Self CPU samples.

CSV does not carry a source filename, full signature, workload, or build configuration. An optional conditions JSON (schema 1) binds `profile_sha256`; optional `source_identity` records the known compilation unit, `source_sha256` records artifact identity, `workload` records a nonempty workload object, and `build_conditions` records at least `metaeditor_build`, `profiling_optimizations`, `profiling_inlining`, `architecture`, and `environment_id`. Optional `elapsed_duration_milliseconds` remains a separate measurement; it is not inferred from samples. Use a documented stable environment identity and observations of actual profiling settings. Missing conditions produce insufficient comparison evidence.

Comparisons match exact unique function names within the recorded compilation-unit context; duplicate names, unmatched functions, and uncertain mappings remain visible. There is no fuzzy matching or assertion of individual included-file identity. Workload, source context, and build conditions must match. Additional required evidence accepts `linked_conditions`, `source_hash`, or `elapsed_duration`. Metric names have the form `OnStart.self_cpu_samples` or `OnStart.self_cpu_percent`. Percentage changes alone establish no overall speed improvement; comparable workloads and repeated timing evidence are needed.

Equivalent integer and digit-string MetaEditor build numbers compare as the same build. The original recorded build-condition representation remains available in `recorded_identity.recorded_build_conditions`.

When required build fields are missing, comparison still examines every available required build setting from hash-linked conditions. Known conflicts produce `incompatible` alongside missing fields such as `build_conditions.architecture`; matching partial settings remain `insufficient_evidence`. Conditions whose export hash does not match cannot supply build-setting evidence. Observed CPU differences remain available for matched functions, while expectations stay `not_evaluable` until all required conditions and evidence are satisfied.

Workload objects and arrays compare recursively by JSON type and value. Booleans, numbers, and strings remain distinct; equal integer and decimal JSON numbers compare as the same numeric value. Type mismatches make conditions incompatible and prevent expectation evaluation.

See native definitions at [MT5 testing reports](https://www.metatrader5.com/en/terminal/help/algotrading/testing_report) and [MetaEditor profiling](https://www.metatrader5.com/en/metaeditor/help/development/profiling). Tests retain genuine sanitized input provenance. UI actions used once to prepare those fixtures are not shipped as runtime automation.
