# Strategy Tester smoke-test workflow

Read this file completely before invoking or interpreting the bundled Strategy Tester runner.

## Invocation

Use the bundled runner when Strategy Tester execution or tester-readiness/preflight validation is requested or needed to complete the task. Use `-PreflightOnly` for readiness validation without launching MT5; run it before the first `-Execute` on a terminal.

MT5 is launched with only `/config`, so it opens the default data directory bound to its installation (under the user's `MetaQuotes\Terminal` folder) and initializes that directory's saved broker account. A saved account can be live, and startup can resume Signals copying; the startup file disables Expert trading but cannot disable signal copying. Before staging, the runner therefore inspects `config\accounts.dat` in the selected and default data directories and records `saved_account_inspection` as `none`, `present`, or `unknown`. A selected `-TerminalDataPath` that differs from the terminal's default data directory is blocked (exit `4`). When the state is `present` or `unknown`, `-Execute` is blocked (exit `4`) unless `-AcknowledgeSavedAccountRisk` is passed. Pass that switch only after the user explicitly confirms in chat, for this run, that the saved account may log in; never infer it from a general request to test. Prefer a dedicated terminal installation without saved accounts. The `accounts.dat` location is an observed terminal layout and is `Not verified in the installed MQL5 CHM`; treat the check as defense in depth. Security-sensitive runner paths must use direct fixed local volumes whose drive letters are registered by the Windows mount manager; mapped network drives, SUBST and raw DOS-device aliases, UNC paths, device paths, junctions, symlinks, mount points, and other reparse-point components are rejected. Use absolute paths:

Direct and profile-based selection require an ordinary `terminal64.exe` with readable Windows major-version-5 metadata. An explicitly incompatible terminal fails with tooling exit `2` before launch; automatic discovery excludes incompatible candidates. The runner repeats validation after it pins the exact terminal image against writes and replacement, and before creating the suspended process. Metadata identifies the supported platform version; it does not authenticate an executable or establish trust.

```powershell
$skillRoot = "<installed skill root containing SKILL.md>"
$runner = [IO.Path]::GetFullPath((Join-Path $skillRoot "scripts\Invoke-Mt5TesterSmoke.ps1"))
powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File $runner -Execute -ExpertPath "<absolute-ex5-path>" -SetPath "<absolute-set-path>" -Symbol "<symbol>" -Period "<period>" -FromDate "YYYY.MM.DD" -ToDate "YYYY.MM.DD" -Model <0-4> -Deposit "<deposit>" -Currency "<currency>" -Leverage "<leverage>" -ExecutionMode "<mode>" -OutputDirectory "<new-absolute-output-directory>"
```

When the user supplies `.mq5` source, compile it first with the MetaEditor wrapper and require exit code `0`. Pass the exact freshly emitted `.ex5` and the path emitted as `MQL5_COMPILE_RECEIPT` to the smoke runner using `-CompilationReceiptPath "<absolute-json-path>"`. This applies to both `-PreflightOnly` and `-Execute`. The runner reads the EX5 hash from the receipt, checks the source, EX5, and retained compiler log hashes and lengths, verifies that the log's final error/warning counts agree, and holds those bytes open through cleanup. It rejects failed, syntax-only, malformed, unsupported, or stale receipts before staging or terminal launch. The recorded compiler version must remain its original nonblank string; arrays, objects, null, numbers, and booleans are rejected without imposing another version format. The result JSON records the receipt hash, compilation run ID, compiler build, counts, and verified file hashes under `inputs.compilation_receipt`.

For an independently supplied trusted `.ex5` without a receipt, the existing `-ExpectedExpertSha256 "<64-hex-sha256>"` workflow remains available. One of the two is required; without either, the runner fails with exit `2` before staging, so an older artifact left by a failed compilation cannot be tested. If both parameters are supplied, their EX5 hashes must agree. The runner never guesses which historical receipt to select. Never substitute a stale sibling or previously installed artifact. Treat a receipt/hash mismatch as tooling failure, not as tester evidence. A receipt records the root source and historical compiler image; it does not fingerprint included `.mqh` files, the preset, or runtime dependencies and does not require the old compiler to remain installed. Receipts are unsigned local evidence and do not establish that an EX5 is trustworthy.

The receipt JSON must have one object at its root, with object-valued source, EX5, log, and compiler records and string-valued kind, run ID, and status. Wrapping those values in arrays is unsupported and fails before tester staging or launch. Receipt bytes must decode without replacement; UTF-8 and established BOM-marked UTF-16/UTF-32 inputs remain supported. Invalid physical encoding fails before staging or launch, while a legitimate literal replacement character remains ordinary text.

## Configuration and markers

The marker-file reader and marker-set limits are shared with scenario-batch validation. Files use strict UTF-8 with an optional UTF-8 BOM and cannot exceed 65,536 bytes. An optional label contains 1–64 ASCII letters, digits, underscores, dots, or hyphens. The tester deduplicates exact markers from the command line and file, then allows at most 64 unique markers totaling at most 8,192 characters. These checks happen before staging or terminal launch; they preserve the marker file's exact byte hash in successful preflight evidence.

Resolve the symbol, period, dates, tester model, deposit, deposit currency, leverage, execution mode, and inputs from the task, saved profile, project, or selected existing tester configuration. A `.set` file controls EA inputs for this runner and does not supply the tester account or execution settings. Pass exactly one EA input choice: `-SetPath "<absolute-set-path>"` for the selected preset, or `-UseExpertDefaults` when no preset is selected. No additional acceptance of defaults is required. The runner rejects omitted or conflicting input-source switches. Report the settings used; request missing information only when the correct configuration cannot be determined.

The result records `saved_account_inspection`, `saved_accounts_detected`, the terminal's `default_data_directories`, `selected_data_directory_is_default_for_terminal`, `saved_account_risk_acknowledgement_required` (true when the state is `present` or `unknown`), and `saved_account_risk_acknowledged` (whether the switch was supplied). None of these fields proves account isolation. The runner only observes logs; it never injects a marker into the EA. For an EA self-test, pass one literal `-ExpectedLogMarker` only when the exact compiled fixture and selected inputs or preset are already arranged to emit that unique nonce and passing result. Every marker must use the case-sensitive form `MQL5_CODING_PASS:<32-64 hex nonce>[:optional-label]` and must be the complete application-message payload; input or preset echoes do not count, and a longer labeled marker cannot satisfy its shorter prefix. This prevents ordinary platform text from being promoted to an application pass. Do not add tester-only output to the EA unless the user's task includes that code change. When multiple independent markers are required, write one non-empty protocol marker per line in a UTF-8 file and pass `-ExpectedLogMarkerFile "<absolute-path>"`; do not repeat the named command-line parameter. The result JSON records SHA-256 commitments and per-marker match results without disclosing marker plaintext. Select exactly one mode: `-Execute` performs the run; `-PreflightOnly` validates discovery, exclusive output ownership, hash-bound staging writes, configuration, journal readability, and process-isolation preconditions without starting MT5.

## Isolation and evidence integrity

An `-ExpectedLogMarkerFile` must contain at least one non-empty protocol marker. An empty file or a file containing only blank lines is rejected even when `-ExpectedLogMarker` also supplies a valid command-line marker.

The runner refuses to start when the bound MT5 terminal image is already running through its selected path or an accessible hard-link, junction, symlink, or short-path alias; close that terminal yourself or select a dedicated installation, then rerun (the runner never stops it). It requires mount-manager-registered direct fixed-volume drive mappings, repeatedly revalidates them, correlates each opened path-entry handle with the expected volume serial, rejects mapped network, SUBST, and raw DOS-device drive letters, rejects reparse points in every security-sensitive local path chain, and leases those directory and file entries through staging, execution, evidence capture, and result creation. Directory leases deny data-write and delete sharing, while pinned temporary guard files keep writable leaf directories nonempty until path-based work finishes; ordinary child creation remains permitted. File-leaf leases preserve the write sharing needed for journals while denying pathname replacement. Existing and newly discovered journal files are read through pinned streams, so a pathname replacement cannot substitute different evidence bytes. It holds its exclusive runner lock inside the terminal data directory, pins and revalidates that directory's `origin.txt` binding, claims a new output directory without overwriting another run, and executes a unique hash-bound staged copy of the `.ex5`. It records the selected terminal executable's hash and stable Windows volume/file identity, holds that exact image open without write or delete sharing, and verifies that the suspended child maps to the pinned identity before resume. It also holds read locks on the exact terminal-origin, staged expert, preset, and startup-config bytes through execution so they cannot be replaced or rewritten while MT5 reads them. It also pins the recorded output-owner, canonical-config, and copied-report bytes through final integrity verification so their recorded hashes are not stale when the result is prepared. Its generated startup file requests local-only agents, disabled optimization and visual mode, disabled live trading, and terminal shutdown. The effects of those startup keys are `Not verified in the installed MQL5 CHM`; treat them as defense-in-depth requests, not proof of isolation. The runner creates the terminal suspended, assigns it to a kill-on-close Windows Job Object, verifies its process and executable-file identity, and only then resumes it. If Job Object assignment fails, it verifies termination of the still-suspended process and records the created PID and cleanup result instead of claiming an unchecked cleanup. On every normal or timed-out exit it terminates the owned job and requires the job to report zero active processes before accepting evidence, so short-lived intermediate parents cannot hide surviving descendants.

Terminal-process discovery is point-in-time and cannot prevent a separately launched terminal from starting and exiting between checks; do not open the bound terminal during a run. Accessible process images are compared by stable file identity rather than pathname text, and an unreadable process named `terminal64.exe` blocks the run. This is defense in depth, not a guarantee against a hostile higher-privilege process whose image identity cannot be inspected. The runner never automatically deletes staged files or directories by pathname; both execution and preflight JSON list preserved unique paths for identity-aware manual cleanup. It rejects replaced or modified journal prefixes, bounds terminal success to the selected startup-config window, requires exactly one unambiguous exact-expert test window with its pass and markers inside that window, reads only bounded bytes appended during the run, and removes caller-supplied marker plaintext plus common password, token, API-key, authorization, and secret values from JSON excerpts. It records only marker hashes and match results. Runtime dependencies outside the `.ex5` are not copied automatically and must already be installed for the selected terminal.

## Result interpretation

Interpret the runner exit code exactly:

- `0`: preflight staging passed, or the result JSON reports `engine_smoke_passed` or `application_marker_passed`.
- `1`: tester execution completed but correlated evidence failed.
- `2`: invalid input, tooling, evidence capture, or cleanup failure.
- `3`: the spawned tester terminal timed out.
- `4`: the run was safely blocked before any MT5 process started, such as by an already-running bound terminal.

These codes apply after PowerShell successfully parses and binds the script invocation. A host-level syntax or duplicate-parameter error, or a pre-output initialization failure such as a blocked native-helper load, can leave no runner JSON. Treat every missing runner result as an invocation/tooling failure; do not infer success from the host exit code alone.

Do not treat MT5 process exit `0`, `automatic testing finished`, or report creation alone as success. Require the JSON evidence for the pinned terminal-image identity, exact config, expert, symbol, period, dates, agent initialization, engine pass, terminal result, ordered evidence, unchanged locked staging, an emptied owned Job Object, and no residual matching terminal. An expected marker counts only as the complete application-message payload after the exact correlated test-start line and before its correlated engine-pass line, with both inside the same unambiguous bounded test window. Without caller-supplied application markers, describe a pass only as Strategy Tester engine smoke completion; it does not prove strategy correctness or full-date execution.

## Limitations

The installed MQL5 CHM does not specify tester-journal record syntax. The runner accepts only explicitly sample-backed tab-delimited `Tester` and `Core <number>` layouts and fails closed on unknown layouts; treat this parser as version-sensitive until validated against the selected terminal.

Record the terminal build and retain the result JSON from a real fixture run. A passing fixture supports the observed journal layout and selected configuration; revalidate after upgrading the terminal. This does not establish strategy correctness or broker compatibility.

The integrity mode intentionally rejects UNC paths and any reparse-point component, including OneDrive or other filesystem-provider directories marked as reparse points. Use ordinary local directories for the terminal, source artifacts, preset, and output.

The runner requests Strategy Tester operation, but the terminal may still initialize its saved broker account or other saved terminal state before testing. Do not describe it as strictly offline or as proven Strategy-Tester-only. Strict offline validation requires a dedicated credential-free terminal and preloaded history.

Never execute an untrusted `.ex5` with this runner. Its process and staging isolation are not a security sandbox for code executed by MetaTrader.
